# Module 6 checkpoint: answers

Reference answers to the [checkpoint](README.md#checkpoint-answer-in-your-own-words), using the traces in [Reference results](README.md#reference-results-qwen34b-instruct-2507-q4_k_m). This file isn't part of the search corpus (only `README.md` is), so it can quote the tasks and their answers.

## 1. Who actually executes a tool, the model or your code? What exactly does the model produce?

**Your code.** The model only produces text: the name of a tool and its arguments as a string of JSON.
- **Native:** Qwen writes `<tool_call>{"name": "calculator", "arguments": {…}}</tool_call>`, and Ollama parses it into the `tool_calls` field.
- **Text agent:** the model writes `Action:` and `Action Input:` lines, and your regex in `text-loop.ts` finds them.

Either way, `runTool` in `tools.ts` parses the JSON, checks it, runs the function and sends the result back as a new message. In the trace:
- `→ calls calculator {"expression":"17.5 * 2340 / 100"}` is the model's request;
- `── tool calculator · 0.0 s` is your code.

The model is idle while a tool runs. It can't pause mid-reply and wait for the result, so every tool call costs one more model call. A task with N tool calls needs at least N + 1 model calls (t01: 1 tool call, 2 model calls).

## 2. Your text agent and your native agent do the same job. What does native tool calling add, and what stays the same?

**The same:**
- the loop, the tools' code, `runTool` and the step limit;
- resending the whole conversation on every call, because the API is stateless;
- the model making every decision.

**Native adds:**
- a format the model was trained on (Qwen's chat template);
- parsing done by Ollama instead of your regex, with no ``` fences to strip;
- tool calls that come back as structured data, with ids that link each result to its call.

**Native loses:**
- **An explicit "done" signal.** A reply without a tool call counts as the answer, so "I will read that file" ended t09.
- **The written Thought.** On t03 the text agent's Thought led it to the calculator; the native agent answered straight away and got it wrong.

It also costs more prompt: 532 tokens against 339 for the text agent, because of the JSON definitions plus the template's own instructions. Native tool calling is still a prompt, just one the model saw in training.

**On your machine,** with this model and these tasks, it bought no measurable reliability: native 3/6, text 4/6, and zero errors for both. The decisions mattered more than the format.

## 3. Why does the text agent need a stop sequence? What did you see with `--no-stop`?

The model just continues text. After `Action Input: {…}`, the most likely continuation is `Observation: …`, because that's the pattern in the prompt. It can't run the tool, so it writes a plausible result. The stop sequence `Observation:` ends the reply right there, so the real result from your code takes its place.

With `--no-stop`, the model wrote the Observation itself in both runs:
- **t01:** `Observation: 409.5`, then a Final Answer saying "17.5% of **7,340** is 409.5". The guessed number was right, because the arithmetic was easy, but it miscopied the question.
- **t02:** `Observation: 2.5`.

For a `read_file` call, it would have had to make up the file's contents, and they'd have looked just as convincing. The made-up text also costs decoding time: ~35 tokens (~4 s) on t01, and ~70 tokens (~9 s) on t02.

## 4. Why do agents compound errors? Use a number, and an example from your traces.

Every step builds on the ones before it, so the chances multiply. If each step is right 90% of the time, 3 steps are all right 0.9³ ≈ 73% of the time, and 5 steps only 0.9⁵ ≈ 59%. A wrong step doesn't stay contained either: everything after it treats it as fact.

**t03, native:**
- Steps 1 and 2 were perfect: `list_files` found the CSV, and `read_file` returned every row.
- Step 3 made two mistakes on top of that correct result. It included the September row (54.20), and it added the numbers in its head.
- It answered €260.80 instead of 228.80. Its own six numbers don't even add up to 260.80.

**t02** shows the other way it goes wrong: a bad *plan* at step 1. The model decided it already had what it needed. Every later step was consistent with that plan, so the answer looked fine ("2.5 times the original amount") and was useless.

The eval's error column showed **0** in both cases. It counts crashes and tool errors, not wrong decisions, so a wrong answer can be completely silent.

## 5. Why are a tool's arguments untrusted input? Give two places in this module's code that deal with that.

The arguments are text generated by a model, and that model can be confused, or steered by anything it has read: a file, an email, a search result. That's indirect prompt injection. Anyone who can put text in front of the model can influence what it asks your code to do. So treat the arguments like input from a stranger.

In the code:
- **`read_file`'s path guard** (`tools.ts`): `resolve()` the path first, then refuse anything that doesn't start with the sandbox folder. That blocks `../../.env`, `inbox/../../../.env` and `/etc/passwd`.
- **The calculator parses arithmetic itself** instead of calling `eval`. `eval` would run any JavaScript the model wrote.
- **`runTool`** returns an `Error: …` result instead of crashing when:
  - the JSON doesn't parse;
  - the arguments aren't an object;
  - a string argument is missing (`stringArg`).
- **Least privilege:**
  - every file tool is read-only;
  - `list_files` skips dotfiles;
  - reads are capped at 4,000 characters.

**t09 showed the limit of these guards.** The injected email didn't make the agent call any tool. Its request ended up in the *summary* instead, presented as if the supplier had asked for your `.env` file. Code can check a path, but not a sentence. That's why anything that writes or sends needs a human's approval (exercise 1).

## 6. Agentic RAG vs. Module 5's pipeline: what does letting the model search buy you, and what does it cost on your machine?

**What it buys:**
- **The model can rewrite the query.** On t05 it searched for "vector dimension size", which is closer to how the notes phrase it than the question was.
- **It can skip the search when none is needed,** as on t04 (no tool at all).
- **It can search again with other words,** and combine search with other tools.

**What it costs:**
- **Three decisions the model can get wrong,** decisions that Module 5's code made for it:
  - **whether to search:** it didn't on t06 and t07;
  - **what to search for:** on the forced search it copied the question, and repeated Module 5's r12 miss;
  - **whether to search again:** it never did. It guessed an author ("the course's instructor") and hedged in the same reply.
- **Time.** At least two model calls instead of one, and the first one reads ~530 tokens of tool definitions. Then the ~600 tokens of search results are read in a second call. t05 took 37–82 s, against ~18 s for a Module 5 answer.

For these questions, on your machine, Module 5's fixed pipeline was faster and at least as accurate. A common middle ground: always search once with the question, as Module 5 does, and let the agent search again only when the results don't answer it.
